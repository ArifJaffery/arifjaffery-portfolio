Case WP-HO-01Type Post-handover security reviewStatus ContainedData Anonymised

The vendor left. Their admin accounts didn't.

A WordPress site on Windows Server and IIS was handed over by a software agency. A brief outage prompted a health check, which turned up two agency administrator accounts still active, admin logins over plain HTTP, and a handful of hardening gaps. This file records what was found, how, and every command used.

Compromise foundNo evidence
Exposed admin accounts2 disabled, backed up
Outage causeOutside the server
Data lossNone

01Summary

The site went down for a short period and recovered on its own. While investigating, the team reviewed who could administer WordPress and found two Administrator accounts belonging to the agency that originally built the site. One had been created years earlier; the other had installed a plugin only a couple of weeks before the review.

Neither account showed signs of malicious use. The risk was the access itself: full control of the site held by a third party with no active engagement, used over unencrypted connections to the server's raw IP address. Both accounts were disabled in place, with their data backed up so access can be restored if the agency is re-engaged.

04Findings

High

Two vendor Administrator accounts still active

Full site control held by a third party after hand-over. One account had installed a plugin two weeks earlier, with no change record on the client side.

High

Admin logins over plain HTTP to the raw IP

Pages created via http://203.0.113.10 show credentials were being sent unencrypted across the internet.

Medium

Usernames published by the REST API

/wp-json/wp/v2/users listed every author's login name, giving attackers half of each credential.

Medium

MySQL 8.0 past end of life

No further security patches. The X Plugin also listened on all interfaces on port 33060.

Medium

No web application firewall

Defender scans files on disk; nothing filtered login brute-forcing, plugin exploits or bad bots before they reached WordPress.

Low

Desktop software on a production server

A browser and code editor used about 1.5 GB of the 8 GB, and a download manager of unknown licence origin was installed.

Low

Hard-coded IP links in the site

Footer and social-sharing links pointed at the raw IP. They broke once public HTTP was removed.

Info

No signs of compromise from outside

No spam content, hidden links, redirects or injected scripts; nothing suspicious indexed by search engines.

05The outage

Each log answers a different question. Reading them in order narrowed the cause quickly.

SourceQuestionWhat it showed
IIS access logsDid the site return server errors?No 5xx responses in 24 hours
HTTP.sys (HTTPERR)Did the app pool crash or stall?Only idle timeouts, client cancels and rejected bot requests
MySQL error logDid the database crash?Only clean "Normal shutdown" and "ready for connections" pairs
Windows event logsDid a service or the VM restart?Used to confirm restart times

With no error recorded anywhere on the server, requests most likely never reached it: a network or VMware-side interruption. The fix was observability. External monitors now record the exact start and end of any future outage, and which layer failed.

06Vendor accounts

WordPress has no "deactivate" button, and deleting a user forces you to reassign their content. The approach used here disables the account in place, so it can be restored exactly if the Vendor is re-engaged.

  • Back up the user's row and all of its metadata into side tables first.
  • Remove the role so the account can do nothing.
  • End sessions and delete application passwords, which is how AI tools and integrations usually log in.
  • Replace the password hash and email, so neither login nor "Forgot password" can get back in.

Before disabling, confirm you can log in with a remaining administrator, and check for access the vendor may hold outside WordPress.

G. Inspect accounts

Read-only
Every administratorSQL
SELECT u.ID, u.user_login, u.user_email, u.user_registered FROM wp_users u
JOIN wp_usermeta m ON m.user_id = u.ID
WHERE m.meta_key = 'wp_capabilities' AND m.meta_value LIKE '%administrator%';
One account, its role and app passwordsSQL
SELECT ID, user_login, user_email, user_registered FROM wp_users WHERE user_login = 'vendor_ai';

SELECT meta_key, LEFT(meta_value, 200) AS value FROM wp_usermeta
WHERE user_id = 12 AND meta_key IN ('wp_capabilities','session_tokens','_application_passwords');

Application passwords record the name of the tool that used them, when, and from which IP. Read them before disabling.

H. Back up, then disable

Shown for vendor_ai (ID 12); repeat with ID 4
Allow the backup tables to be createdSQL
-- Fixes "ERROR 1067: Invalid default value for 'user_registered'". Session only.
SET SESSION sql_mode = '';
Back up the user and its metadataSQL
CREATE TABLE zz_backup_vendor_ai_user     AS SELECT * FROM wp_users    WHERE ID = 12;
CREATE TABLE zz_backup_vendor_ai_usermeta AS SELECT * FROM wp_usermeta WHERE user_id = 12;

SELECT ID, user_login, user_email FROM zz_backup_vendor_ai_user;
SELECT COUNT(*) FROM zz_backup_vendor_ai_usermeta;
Disable the accountSQL
UPDATE wp_usermeta SET meta_value = 'a:0:{}' WHERE user_id = 12 AND meta_key = 'wp_capabilities';
UPDATE wp_usermeta SET meta_value = '0'      WHERE user_id = 12 AND meta_key = 'wp_user_level';
DELETE FROM wp_usermeta WHERE user_id = 12 AND meta_key IN ('session_tokens', '_application_passwords');
UPDATE wp_users SET user_pass = 'DISABLED', user_email = 'disabled-vendor-ai@invalid.local' WHERE ID = 12;
VerifySQL
SELECT meta_key, meta_value FROM wp_usermeta WHERE user_id = 12 AND meta_key IN ('wp_capabilities','wp_user_level');
-- Expect: a:0:{}  and  0
SELECT user_login, user_email, user_pass FROM wp_users WHERE ID = 12;

I. Restore an account

If the vendor is re-engaged
Exact restore from the backup tablesSQL
UPDATE wp_users u JOIN zz_backup_vendor_ai_user b ON b.ID = u.ID
SET u.user_pass = b.user_pass, u.user_email = b.user_email;

UPDATE wp_usermeta m JOIN zz_backup_vendor_ai_usermeta b ON b.umeta_id = m.umeta_id
SET m.meta_value = b.meta_value;

INSERT INTO wp_usermeta
SELECT * FROM zz_backup_vendor_ai_usermeta b
WHERE NOT EXISTS (SELECT 1 FROM wp_usermeta m WHERE m.umeta_id = b.umeta_id);
Partial restore without a backupSQL
UPDATE wp_usermeta SET meta_value = 'a:1:{s:6:"editor";b:1;}' WHERE user_id = 12 AND meta_key = 'wp_capabilities';
UPDATE wp_usermeta SET meta_value = '7' WHERE user_id = 12 AND meta_key = 'wp_user_level';
UPDATE wp_users SET user_email = 'contact@vendor.example' WHERE ID = 12;

Then set a new password in wp-admin. Prefer Editor; grant Administrator only if they must install plugins.

J. IIS bindings and HTTPS

Close public HTTP, keep server-side access
Current bindings and WordPress applicationPowerShell
Import-Module WebAdministration; Get-WebBinding -Name "Default Web Site" | Select-Object protocol, bindingInformation
Get-WebApplication -Site "Default Web Site" | Select-Object path, PhysicalPath, applicationPool
HTTP for the server itself onlyPowerShell
New-WebBinding -Name "Default Web Site" -Protocol http -Port 80 -IPAddress 127.0.0.1

Restores http://127.0.0.1/wordpress/wp-admin on the server without exposing HTTP to the internet.

Optional: public HTTP redirected to HTTPS, localhost exemptweb.config (site root)
<rule name="Force HTTPS" stopProcessing="true">
  <match url="(.*)" />
  <conditions>
    <add input="{HTTPS}" pattern="off" />
    <add input="{HTTP_HOST}" pattern="^(localhost|127\.0\.0\.1)$" negate="true" />
  </conditions>
  <action type="Redirect" url="https://www.example.com/{R:1}" redirectType="Permanent" />
</rule>

Goes in the Default Web Site root web.config, not the WordPress folder, which holds the permalink rules.

08Hand-over checklist

What to do on the day any agency or contractor hands a site back, so this case doesn't repeat.

  • Inventory every adminList all WordPress administrators and give each one a known owner.
  • Disable vendor accountsBack up, remove the role, revoke app passwords, lock the password and email.
  • Rotate shared secretsThe main admin password, database password and any Windows logins the vendor knew.
  • Check access outside WordPressRemote Desktop, FTP, hosting portal, domain and DNS, analytics and search console.
  • HTTPS only, by domainNo admin logins via the raw IP; public HTTP removed or redirected.
  • Hide usernamesBlock the public users endpoint and rename the default admin account.
  • Put a firewall in frontA WAF such as a free CDN tier, plus a WordPress security plugin with two-factor login.
  • Monitor from outsideWebsite, keyword and port checks with email alerts.
  • Patch the stackWindows, PHP, plugins, and a supported MySQL release.
  • Prove the backupsDaily database and file backups stored off the server, with a tested restore.
