Security hardening case study

Hardening a public WordPress server, from the edge gateway down to the config file

A single internet-facing Windows VM running WordPress on IIS. I reviewed it layer by layer, closed remote-admin exposure, and locked down the host, the web server and the application without taking the site offline.

The work

Controls by layer

Each control lists what changed, why it matters, and the command or setting behind it. Select a layer, then open any item.

    Web server

    The site's web.config, before and after

    The original file only handled WordPress permalinks. The hardened version blocks direct requests for sensitive files, stops the server advertising its PHP version, and adds browser protections. The permalink rule is unchanged.

    Request filtering added

    + <directoryBrowse enabled="false" />
+ <security>
+   <requestFiltering removeServerHeader="true">
+     <hiddenSegments>
+       <add segment="wp-config.php" />
+       <add segment="xmlrpc.php" />
+       <add segment="debug.log" />
+     </hiddenSegments>
+   </requestFiltering>
+ </security>

    Access control

    Giving people access without administrator rights

    Content staff and contractors need to work on the site, not on the server. Access is granted at two separate layers, and each is held to the least it needs: a WordPress role for the person, and a restricted MySQL account for the application.

    PersonSigns in at wp-login.php with their own username
    WordPress roleDecides what this person may do in the dashboard
    MySQL accountOne shared login the site uses for every request
    DatabasePrivileges cap what the whole site can change

    How the role was sized

    1. Started at the lowest role

      Created a test account directly in the database as a Subscriber.

    2. Confirmed the sign-in

      The new account logged in to the dashboard on the first attempt.

    3. Found the gap

      The Pages menu was missing, so the existing Avada pages could not be opened. Subscribers lack the edit_pages capability.

    4. Raised it one step at a time

      Editor is the lowest built-in role that can open the pages, and it still has no access to plugins, themes, users or settings.

    What each built-in role can reach

    Privilege level
      Avada keeps its own role settings for the page builder and reserves its global theme options for administrators. If a page opens in the plain WordPress editor for an Editor, an administrator enables the builder for that role in Avada's options.
      The SQL behind it
      Run against the WordPress database from a MySQL client. Names and passwords are placeholders. If the site uses a table prefix other than wp_, change it in the table names and in the two meta keys.
      Command reference
      The commands behind the work
      Everything was done with built-in Windows tools, run from an administrator PowerShell or Command Prompt. Paths are shown for a default IIS install. Audit commands come first in each block, so the change is always made against a known starting state.
      Next phase
      Recommended next, in priority order
      Hardening is not finished after one pass. These items were scoped during the review and are planned as the follow-up phase.
      • Priority 1
        HTTPS and modern TLS
        Point a domain at the server, issue a Let's Encrypt certificate with win-acme, redirect HTTP to HTTPS, and disable TLS 1.0 and 1.1.
      • Priority 2
        Rotate keys and salts
        Replace the eight WordPress authentication keys, which invalidates every existing session cookie.
      • Priority 3
        Admin login protection
        Two-factor authentication for administrator accounts and a limit on failed login attempts.
      • Priority 4
        Off-server backups
        Scheduled copies of site files and database stored away from the host, with one tested restore.
      • Priority 5
        Enforce rate limits
        Review the log-only data from Dynamic IP Restrictions, tune the thresholds, then switch to blocking.
