Case file · WordPress on Windows Server and IIS · 2026

Inspected.
Defects found.
Rectified.

A company website migrated from WordPress on Linux to WordPress on Windows Server 2025, hosted on a VMware cloud platform. It was hardened in two passes: layer by layer before cut-over, then an attacker's-eye review after launch. Every control, test, command and config is recorded here so the work can be repeated and checked.

How the work ran, in order

Project phases

Phase 1

Pre-cutover hardening

New Windows environment, before go-live
  • Edge gateway: closed internet-facing RDP
  • Windows: 32 inbound rules off, lockout policy, services trimmed
  • IIS: file blocking, headers, rate limiting in log mode
  • WordPress and MySQL: config, permissions, least privilege
  • Access: Editor role for content staff
Incident

Injected links in a backup

Found while restoring the old site's content
  • Spam links present inside the backup itself
  • Twelve read-only SQL checks across the database
  • Five injected links on three pages identified
  • Pattern search found domains a blocklist missed
Phase 2

Post-launch external review

Same-day review and fixes on the live site
  • User enumeration blocked in IIS
  • phpMyAdmin moved to a loopback-only site
  • Core updated to the current security release
  • HTTPS redirect, HSTS and Permissions-Policy
  • Headers grade F → A
Where each control lives

Architecture

Every request passes two firewalls before IIS sees it. Each fix sits at the layer that can enforce it reliably: the edge and host for ports, IIS for paths and headers, WordPress and MySQL for accounts.

    Least privilege at every layer

    Access control

    Content staff need to work on the site, not the server. Access is granted at separate layers and each is held to the least it needs: a WordPress role for each person, a restricted MySQL account for the application, a loopback-only database console, and an admin portal behind several defences.

      Incident response
      Injected links in the database
      
  
      After restoring the most recent backup of the old site, the homepage showed links nobody on the team had written. The infection was inside the backup itself, so it could not be trusted as a clean restore point. It was reported as a compromise, then the database was searched directly for every affected page.
      
  
      
    
      Read-only checks written12
      
    
      Injected links found5
      
    
      Published pages affected3
      
    
      Missed by the first report2
      
  
      

  
      
    
      What an injected link looks like
      
      
      2 injected links
      
      
    
      The attacker drops a link into the middle of a normal sentence, using the bare address as the link text.
      
    
      About us page
      The company stands as a trusted http://spam-site-one.example entity in the realms of real estate, construction law, and conveyancing.
      
    
      Services page
      Our Building http://spam-site-two.example Inspectors are highly skilled, qualified and, where required, licensed building inspectors.
      
    
      Stored HTML in wp_posts.post_content
      <p>Our Building <a href="http://spam-site-two.example">http://spam-site-two.example</a> Inspectors are highly skilled, ...</p>
      
  
      

  
      
    
      HomeA hidden link inside the main heading, which also leaked into the page description shown to Google and social media.Seen on page
      
    
      HomeA thesis-writing service presented in the welcome text as a "trusted partner".Seen on page
      
    
      HomeA gambling site inserted into the "Get in Touch" section.Seen on page

      ServicesA second unrelated overseas domain placed mid-sentence in the inspector description.Found by scan
      
  
      

  
      How the investigation went
      
  
        
    
      1. Spotted it after a restore
        Three foreign links on the homepage, present in the backup itself. Reported as a compromise, not a cosmetic fault.
        2. 
    
      2. Wrote a read-only scan
        Twelve SELECT checks across posts, post meta, options, users, comments and scheduled tasks. Nothing changed while looking.
        3. 
    
      3. Hit a regex timeout
        MySQL 8 stopped with "Timeout exceeded in regular expression match" on large page-builder content. Rewrote the searches with LIKE.
        4. 
    
      4. Read the exported rows
        Exported the rows with full content and pulled out every link address in each page.
        5. 
    
      5. Found new domains
        Two more pages linked to domains not on the original list. A fixed blocklist would never have found them.
        6. 
    
      6. Searched by pattern
        Changed the scan to list any link leaving the site's own addresses, then prepared an exact removal statement for each one.
        7. 
  
      

  
      The twelve checks
      
  
      
    
      wp_postsKnown bad domains in contentPages, posts and saved revisions.
      
    
      wp_postmetaKnown bad domains in post metaPage-builder data and SEO descriptions.
      
    
      wp_optionsKnown bad domains in optionsWidgets, theme settings and the tagline.
      
    
      wp_postsSpam keywordsGambling, essay-writing and pharmacy terms.
      
    
      wp_postsHidden linksStyled invisible to visitors but not to search engines.
      
    
      wp_postsAny external linkEvery published page that links away from the site.
      
    
      posts · optionsInjected codeScripts, iframes and obfuscated functions.
      
    
      wp_optionsCore settingsSite address, admin email, registration, default role.
      
    
      wp_usersAdministrator accountsEvery admin, recent users, ownerless privileges.
      
    
      wp_postsRecently changed contentModification dates against real editing activity.
      
    
      cron optionScheduled tasksCron hooks that could put the links back.
      
    
      comments · termsComments and categoriesLinks in comments and term descriptions.
      
  
      

  
      The SQL behind it
      
  
      Run in phpMyAdmin (now at 127.0.0.1:8080 on the VM) or any MySQL client. Domains are placeholders. Change wp_ if the site uses another table prefix.
      
  
      

  
      What the incident taught
      
  
      
    
      A backup is not a clean copy
      If the infection predates the backup, restoring it restores the attacker's work too.
      
    
      Search for the pattern
      Attackers rotate domains. Listing every outbound link finds what a blocklist misses.
      
    
      Look before changing
      Read-only queries first, a database backup second, a narrow REPLACE on one row last.
      
    
      Dates can mislead
      A link written straight into the database doesn't update the page's modified date.
      
    
      The database is half the job
      Injected content usually comes with a backdoor in plugin, theme or upload files.

      C:\inetpub\wwwroot\wordpress\web.config · current
      <?xml version="1.0" encoding="UTF-8"?>
<configuration>

  <system.webServer>

    <!-- Default document -->
    <defaultDocument>
      <files>
        <add value="index.php" />
      </files>
    </defaultDocument>

    <!-- Never list folder contents -->
    <directoryBrowse enabled="false" />

    <!-- Turn off IIS output/kernel caching for WordPress so pages are never
         served from memory before the rewrite rules below can run -->
    <caching enabled="false" enableKernelCache="false" />

    <!-- Block direct access to sensitive files (returns 404) -->
    <security>
      <requestFiltering>
        <hiddenSegments>
          <add segment="wp-config.php" />
          <add segment="xmlrpc.php" />
          <add segment="debug.log" />
        </hiddenSegments>
      </requestFiltering>
    </security>

    <!-- Hide the PHP version and add security headers -->
    <httpProtocol>
      <customHeaders>
        <remove name="X-Powered-By" />
        <remove name="X-Content-Type-Options" />
        <add name="X-Content-Type-Options" value="nosniff" />
        <remove name="X-Frame-Options" />
        <add name="X-Frame-Options" value="SAMEORIGIN" />
        <remove name="Referrer-Policy" />
        <add name="Referrer-Policy" value="strict-origin-when-cross-origin" />
        <!-- Limit browser features the site doesn't use -->
        <remove name="Permissions-Policy" />
        <add name="Permissions-Policy" value="camera=(), microphone=(), payment=(), usb=()" />
        <!-- HSTS: browsers always use HTTPS for this domain.
             Set to 1 year after a week of testing at 1 day (86400).
             Every address on this domain must work over HTTPS. -->
        <remove name="Strict-Transport-Security" />
        <add name="Strict-Transport-Security" value="max-age=31536000" />
      </customHeaders>
    </httpProtocol>

    <!-- WordPress rewrite rules -->
    <rewrite>
      <rules>

        <!-- Send all HTTP traffic to HTTPS.
             {REQUEST_URI} keeps the /wordpress part of the address.
             Change Temporary to Permanent once you have tested it. -->
        <rule name="HTTPS redirect" stopProcessing="true">
          <match url="(.*)" />
          <conditions>
            <add input="{HTTPS}" pattern="off" />
          </conditions>
          <action type="Redirect" url="https://{HTTP_HOST}{REQUEST_URI}" redirectType="Temporary" />
        </rule>

        <!-- ===== Hide usernames from the public ===== -->

        <!-- Author pages like /wordpress/author/admin/ go to the home page -->
        <rule name="Block author pages" stopProcessing="true">
          <match url="^author/.+" />
          <action type="Redirect" url="/wordpress/" redirectType="Permanent" />
        </rule>

        <!-- ?author=1 lookups go to the home page -->
        <rule name="Block author query" stopProcessing="true">
          <match url=".*" />
          <conditions>
            <add input="{QUERY_STRING}" pattern="(^|&amp;)author=\d+" />
          </conditions>
          <action type="Redirect" url="/wordpress/" appendQueryString="false" redirectType="Permanent" />
        </rule>

        <!-- REST API users list: 404 for visitors who are not logged in -->
        <rule name="Block REST users path" stopProcessing="true">
          <match url="^wp-json/wp/v2/users" />
          <conditions>
            <add input="{HTTP_COOKIE}" pattern="wordpress_logged_in_" negate="true" />
          </conditions>
          <action type="CustomResponse" statusCode="404" statusReason="Not Found" statusDescription="Not Found" />
        </rule>

        <!-- Same list via ?rest_route=/wp/v2/users -->
        <rule name="Block REST users query" stopProcessing="true">
          <match url=".*" />
          <conditions>
            <add input="{QUERY_STRING}" pattern="rest_route=(/|%2F)wp(/|%2F)v2(/|%2F)users" />
            <add input="{HTTP_COOKIE}" pattern="wordpress_logged_in_" negate="true" />
          </conditions>
          <action type="CustomResponse" statusCode="404" statusReason="Not Found" statusDescription="Not Found" />
        </rule>

        <!-- ===== End hide usernames ===== -->

        <rule name="WordPress Rule" stopProcessing="true">
          <match url=".*" />
          <conditions logicalGrouping="MatchAll">
            <add input="{REQUEST_FILENAME}" matchType="IsFile" negate="true" />
            <add input="{REQUEST_FILENAME}" matchType="IsDirectory" negate="true" />
          </conditions>
          <action type="Rewrite" url="index.php" />
        </rule>

      </rules>
    </rewrite>

  </system.webServer>

</configuration>

add_filter( 'rest_endpoints', function ( $endpoints ) {

        exit;

      Phase 2 · same-day timeline, local time
      Lessons learned
      
  
      Two short outages happened during Phase 2. Both came from changes on the server, and both were caught by re-testing straight after the change.
      
  
      
    
      10:57
      External review starts
      Headers grade F. Three usernames, an open database console, outdated core and plugin found.
      
    
      11:08 – 11:25
      WordPress snippet, then IIS rules
      The snippet hid the user list only some of the time. The fix moved into IIS, where it doesn't depend on WordPress.
      LessonEnforce security at the layer that can't be switched off by accident.
      
    
      11:33
      Rules loaded but old pages still served
      PowerShell proved the rules were live. Requests with a query string were blocked; plain URLs returned old author pages from the IIS kernel cache.
      LessonDisable kernel caching for dynamic apps, and re-test with cache-busting URLs.
      
    
      11:48
      User enumeration closed
      Confirmed from a phone on mobile data: 404 on the user list, author pages redirect home.
      
    
      11:54
      IP restriction on phpMyAdmin didn't hold
      The login page stayed reachable from outside despite the allow-list.
      LessonIf a tool is only used on the server, bind it to 127.0.0.1 instead of filtering by visitor IP.
      
    
      12:05
      Outage: Default Web Site stopped
      The site was stopped while creating the new phpMyAdmin site. Restarted within a minute.
      
    
      12:07
      phpMyAdmin private
      Not Found from outside; working at 127.0.0.1:8080 on the VM.
      
    
      12:22
      WordPress core updated
      Moved to the current security release after a VMware snapshot.
      
    
      12:29
      Outage: root web.config deleted
      Every PHP page returned 404 because the PHP handler lives in the root file. Restored from an earlier copy.
      LessonBack up both config files before every change, and keep the backups outside wwwroot.
      
    
      12:41
      Headers grade A
      HSTS at one year, Permissions-Policy added, PHP version hidden.
