Business case: Harbourline's sale day

Harbourline is an Australian online homewares retailer. On Black Friday about a fifth of its yearly revenue arrives in a few hours, and its old setup, one large app on servers sized by hand, slows down exactly when it matters. Kubernetes is the engine that lets the website grow and shrink with demand.

Harbourline is a fictional example. Its traffic, capacity and targets are illustrative, not measured results.

40×Traffic jump from a quiet night to the sale-launch peak. The old servers were sized by guesswork weeks ahead.
95% idleMost of the year, capacity bought for peak sits unused, yet it still runs out on the day.
1 release / fortnightEvery change ships the whole monolith, so the team freezes code for a month before big sales.
One failure, whole siteA slow search query can exhaust shared threads and take checkout down with it.

The storefront as services

  • storefront: server-rendered web pages
  • search and catalog: product data APIs
  • cart: sessions in ElastiCache
  • checkout: payments via the provider's API
  • orders: queue worker on SQS

What stays outside the cluster

  • Databases: Amazon RDS Multi-AZ
  • Images and media: S3 behind CloudFront
  • Card payments: a PCI-certified provider
  • Queues: SQS, so orders survive pod restarts

Honest trade-offs

  • The team needs Kubernetes and AWS skills, or a platform partner
  • More moving parts to monitor than one server
  • The EKS control plane and Auto Mode carry their own fees
  • A small, steady site may be cheaper on a simpler service

    Push: Azure Pipelines deploys

    The pipeline above runs helm upgrade in each cluster. Simple to start, and approvals live in Azure DevOps. The pipeline needs credentials for every cluster.

    Pull: GitOps with Argo CD

    The pipeline only commits the new image tag to a GitOps repo. Argo CD in each cluster (an ApplicationSet can target all three) pulls and syncs, and fixes drift. Clusters need no inbound access from the pipeline, which suits multi-cloud.

    Keep it portable

    • Only standard Kubernetes APIs in the chart; cloud specifics live in values files
    • Same Terraform module outputs (cluster name, endpoint, OIDC issuer) for every cloud
    • One observability stack (OpenTelemetry, Prometheus, Grafana) across clouds
    • Data stays in one cloud unless you design for replication
    Agentic AI · new

    AI agents that deploy the shop on their own, and stop when they should

    The pipeline builds and publishes a release. An AI agent then operates it. You give it a goal, not a script. It reasons about the cluster, plans the rollout, picks tools from an approved list, runs them, and checks the result against the goal. If the numbers are wrong, it plans again or rolls back. Kubernetes suits this well because every action is an API call and the result is easy to measure.

    Where the agent sits in the platform

    • Triggers: a merged PR, a release in Azure Pipelines, an alert, or a request in chat.
    • Brain: a large language model that reasons in a loop: think, act, observe.
    • Hands: tools exposed through the Model Context Protocol (MCP) or function calling: Kubernetes, Helm, Argo CD and Argo Rollouts, AWS, Prometheus, Azure DevOps.
    • Memory: runbooks, past incidents and previous runs, retrieved when it plans.
    • Identity: its own Kubernetes service account and IAM role through EKS Pod Identity, with least privilege.
    • Brakes: policy checks, human approval for production writes, step and retry limits, and a kill switch.

    Guardrails that make it safe to hand over

    Least privilege

    A dedicated service account and IAM role per agent, scoped to its namespaces. Read access is broad; write access is narrow; Secrets stay out of reach.

    Human in the loop

    Production writes pause for approval in the Azure DevOps environment or in chat. Rollbacks are pre-approved because they move toward safety.

    Prefer GitOps

    For lasting changes the agent opens a pull request, not a live edit. Argo CD applies it, so Git stays the source of truth and drift is fixed.

    Small blast radius

    Canary first, dry runs (--dry-run=server, terraform plan), step and re-plan limits, cost caps, and a kill switch that revokes the agent's role.

    Full audit trail

    Every thought summary, tool call, argument and result is logged with the run ID and linked to the work item, next to the Kubernetes audit log.

    Earn trust in stages

    Start in read-only “advise” mode, then shadow mode, then canary-only writes. Test the agent against recorded incidents before you widen its permissions.

    Production checklist

    Reliability

    • Spread replicas across AZs with topologySpreadConstraints
    • PodDisruptionBudgets so node replacement never drains a whole service
    • Readiness, liveness and startup probes on every container
    • Requests set on every pod so the scheduler and Karpenter size nodes correctly

    Security

    • Private API endpoint, or public restricted to your CIDRs
    • EKS access entries for human and CI access, least-privilege RBAC
    • Pod Identity, one IAM role per service account
    • Secrets encrypted with KMS, NetworkPolicies between namespaces, GuardDuty for EKS

    Operations

    • Everything in Git: Terraform or eksctl for the cluster, Argo CD or Flux for apps
    • Container Insights or Managed Prometheus + Grafana for metrics and logs
    • Upgrade one Kubernetes minor version at a time, test in staging first
    • Back up cluster objects and volumes, for example with Velero

    Cost

    • The control plane is billed per cluster-hour, and Auto Mode adds a fee on its nodes; check the EKS pricing page
    • Let Karpenter consolidate nodes and use Spot for stateless work
    • One NAT gateway per AZ is resilient but costs more; use VPC endpoints for ECR and S3
    • Staying on a version past standard support costs more per hour
