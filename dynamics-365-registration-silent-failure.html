    02

    How I found it

    From "it happens sometimes" to three named causes.

    1. Reproduce and read the response body, not the status

      With the browser Network tab open, a failed registration still came back 200 OK. The body was the giveaway: an empty GUID or an error object where a record ID should be.

      POST /Account/CreateAccount 200 OK Response: "00000000-0000-0000-0000-000000000000"

    2. Audit the client: success was decided by transport, not by data

      The .success callback received portalUserId and never looked at it. It showed the pending-approval screen and even posted the questionnaire to SaveAnswers with the empty ID. Failures of that second call were routed to the same success handler.

    3. Audit the server: every failure was converted into a 200

      Both Dataverse service methods wrapped service.Create in a catch-all that logged and returned Guid.Empty. The controller never checked either return value, cleared the email verification regardless, and serialised whatever came back.

    4. Correlate with the CRM log table

      The services did log before swallowing. Matching failed registration times against log entries named CreateAccount Error and CreatePortalUser Error showed the real Dataverse fault messages. Failures with no matching log entry pointed to the verification check instead.

      Name FunctionName CreatePortalUser Error PortalUserService | CreatePortalUser CreateAccount Error CustomerService | CreateAccount

    5. Explain "sometimes"

      Verification state lives in a static service on the controller. If it is held in memory, an app-pool recycle, a redeploy or a second server instance between "Verify" and "Create account" loses it. The user sees a verified tick; the server says "not verified" with a 200.

    03

    Root causes

    Three silent paths, three contributing defects.

    F1 · VERIFICATION

    "Not verified" returned as 200

    The controller rejected the request but with a success status. Nothing was created; the UI celebrated.

    F2 · ACCOUNT

    Account create swallowed

    CreateAccount returned Guid.Empty on any fault. The portal user was then created against an empty account and also failed.

    F3 · PORTAL USER

    Portal user create swallowed

    The account existed, the blu_portaluser did not. The result was an orphan account and a customer who could never log in.

    Double submitThe Create account button stayed enabled while the request was in flight, so one registration could fire twice.
    Swallowed secondary saveSaveAnswers failures called the success handler, with the empty ID as the key.
    Profile JSON mismatchAnswers were saved as {Number, Answer} but read as {Q, A}, so ABN and account type were always blank for approvers.
    04

    The fix

    Every change, before and after.

    • One response contract{ success, portalUserId } or { success:false, code, message }. No bare GUIDs.
    • Stop at the first failureEach Dataverse step is checked before the next one runs.
    • Compensate, don't orphanIf the portal user fails, the account just created is deleted.
    • Honest, specific messages"Verify again" for what the user can fix; "system is down" for what they can't.

      06

      What I'd tell the next team

      HTTP 200 is not a business outcome

      Transport success and domain success are different facts. Put the domain result in the body and make the client check it.

      A catch that returns a default is a lie

      Returning Guid.Empty from a catch-all hides the error from every caller. If you must catch, the caller must check.

      Multi-record writes need a plan for half-success

      Dataverse calls here aren't in one transaction. Order them, check each, and compensate when a later step fails.

      Write the failing test first

      A spec that fails on the original code is the proof the bug existed, and the guard that it doesn't come back.
