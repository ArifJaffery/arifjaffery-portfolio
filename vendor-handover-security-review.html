The vendor left. Their admin accounts didn't.

A WordPress site on Windows Server and IIS was handed over by a software agency. A brief outage prompted a health check, which turned up two agency Administrator accounts still active, admin logins over plain HTTP, and several hardening gaps. This case file records what was found, how it was traced, and every command used.

Summary

Full site control, held by a third party nobody was watching

The site went down briefly and recovered on its own. While investigating, the team reviewed who could administer WordPress and found two Administrator accounts belonging to the agency that built the site. One dated from the original build; the other had installed a plugin only two weeks before the review, with no change record on the client side.

Neither account showed signs of malicious use. The risk was the access itself, used over unencrypted connections to the server's raw IP address. Both accounts were disabled in place, with their data backed up so access can be restored exactly if the agency is re-engaged.

The outage

Every layer on the server reported healthy

A request passes through five layers on its way to the database. Each layer on the server keeps its own log, and none of them recorded an error during the outage.

Layer 1Network & VMwareProvider network, NAT, VM hostLikely cause
Layer 2HTTP.sysHTTPERR log: only idle timeouts and bot noiseNo faults
Layer 3IISAccess logs: zero 5xx in 24 hoursNo errors
Layer 4PHPNo app-pool crashes in WAS eventsNo crashes
Layer 5MySQLOnly clean "Normal shutdown" entriesClean

With no error anywhere on the server, requests most likely never reached it. The lasting fix was observability: three external monitors now record the exact start and end of any future outage, and which layer failed.

Vendor accounts

Disable in place, keep a way back

WordPress has no "deactivate" button, and deleting a user forces you to reassign their content. Disabling the account directly in the database removes all access while keeping the record, its pages and an exact restore path.

  1. Back upCopy the user row and all its metadata into side tables.
  2. Remove the roleCapabilities set to empty; user level set to 0.
  3. Cut live accessDelete sessions and application passwords used by tools.
  4. Lock the doorReplace the password hash and email so resets can't reach it.

Exact restore from the backup tablesSQL
UPDATE wp_users u JOIN zz_backup_vendor_ai_user b ON b.ID = u.ID
SET u.user_pass = b.user_pass, u.user_email = b.user_email;

Hand-over checklist

Ten things to do the day a vendor hands back a site

  • Inventory every adminList all WordPress administrators and give each a known owner.
  • Disable vendor accountsBack up, remove the role, revoke app passwords, lock password and email.
  • Rotate shared secretsMain admin, database and any Windows logins the vendor knew.
  • Check access outside WordPressRemote Desktop, FTP, hosting portal, domain and DNS, analytics.
  • HTTPS only, by domainNo admin logins via the raw IP; public HTTP removed or redirected.
  • Hide usernamesBlock the public users endpoint and rename the default admin.
  • Put a firewall in frontA WAF in front of the site, plus two-factor login for wp-admin.
  • Monitor from outsideWebsite, keyword and port checks with alerts.
  • Patch the stackWindows, PHP, plugins, and a supported MySQL release.
  • Prove the backupsDaily database and file backups stored off the server, with a tested restore.
