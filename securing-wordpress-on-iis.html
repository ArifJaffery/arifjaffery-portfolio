Infrastructure case study · Windows Server · IIS · VMware Cloud Director · MySQL · WordPress

http://203.0.113.10 → https:// a production WordPress site, traced hop by hop

A small business website ran on plain HTTP, reachable only by its public IP address. I moved it to HTTPS on its own domain, then chased a handshake failure through five layers until I found the real cause in the cloud edge gateway's NAT rules, and finished by cleaning hard-coded addresses out of the database without corrupting it.

Incident log

Symptom, hypothesis, test, finding

Entries are in the order they happened, including the hypotheses that turned out wrong. Ruling things out was most of the work.

Phase 1 · Domain and certificate

Step 1Fixed

Domain redirected straight back to the bare IP

http://www.example.com.au/wordpress → 302 → http://203.0.113.10/wordpress/
  • HypothesisIIS isn't redirecting; WordPress is. It stores its own address in siteurl and home and canonicalises every request to it.
  • FixPinned WP_HOME and WP_SITEURL in wp-config.php, first on http:// to keep the site up, then on https:// once TLS worked end to end.
Step 2Fixed

Browser refused the TLS handshake

ERR_SSL_PROTOCOL_ERROR · "sent an invalid response"
  • CheckedGet-WebBinding showed one https binding, for www. only, with sslFlags 0 (SNI off). The apex domain had no binding at all.
  • CheckedCertificate: wildcard *.example.com.au, private key present, Subject Alternative Name also lists the apex domain. The certificate itself was fine.
  • FixEnabled SNI on the www binding and added a second https binding for the apex domain. Worked around the IIS Manager quirk where the OK button stays greyed after ticking SNI by re-selecting the certificate.
  • ResultSame error. The binding was wrong, but it wasn't the whole story.
Step 3Benign

IIS alert after enabling SNI

No default SSL site has been created. To support browsers without SNI capabilities…
  • AssessedInformational only. It affects clients without SNI support (for example, Internet Explorer on Windows XP). Accepted and documented.

Phase 2 · Isolating the layer

Step 4Key test

Speak plain HTTP to port 443

http://www.example.com.au:443/wordpress/test.html → page loaded
  • Why"Invalid response" during a handshake usually means the other end isn't speaking TLS at all. If port 443 answers a plain HTTP request, something is serving HTTP on it.
  • FindingIt did. Something on the path to port 443 was serving cleartext, which narrowed the search from "certificate problem" to "wrong thing listening, or wrong thing forwarded".
Step 5Ruled out

Who owns port 443 on the VM?

  • Testnetstat -ano | findstr :443 showed 0.0.0.0:443 LISTENING on PID 4, which is http.sys (IIS). No rogue process. The VM's own address was private, so the server sits behind a NAT gateway.
Step 6Gotcha

curl in PowerShell isn't curl

Invoke-WebRequest : A parameter cannot be found that matches parameter name 'vk'.
  • CauseIn Windows PowerShell, curl is an alias for Invoke-WebRequest.
  • FixCalled curl.exe explicitly.
Step 7Ruled out

Bypass the network: test TLS on the server itself

  • Testcurl.exe -vk … --resolve host:443:127.0.0.1 pins the name to loopback, so SNI, the certificate and IIS are all exercised without DNS or the gateway.
  • FindingFull TLS handshake and HTTP/1.1 200 OK from Microsoft-IIS/10.0. IIS, the bindings and the certificate were healthy. The fault was in front of the VM.
Step 8Red herring

"remote party requests renegotiation"

  • HypothesisIIS was requesting client certificates, which HTTP/2 browsers reject with exactly this error.
  • TestSSL Settings on the site and every application under it: all set to Ignore.
  • FindingNot the cause. Schannel reports TLS 1.3 post-handshake session tickets with that wording; it is normal curl output on Windows. Dropped it and moved on.
Step 9Ruled out

DNS and reachability

  • Testping from inside the VM resolved both names to the public IP. From outside, DNS resolved correctly but ICMP timed out.
  • FindingDNS was correct. The timeouts were the edge firewall dropping ICMP, which is expected and harmless for web traffic.
Step 10Root cause

The edge gateway translated port 443 to port 80

curl: (35) schannel: next InitializeSecurityContext failed: SEC_E_INVALID_TOKEN (0x80090308)
  • SignalFrom an outside PC the client sent a TLS hello and got back bytes that weren't TLS. Combined with Steps 4 and 7, port 443 had to be landing on the VM's port 80.
  • FindingIn VMware Cloud Director, a DNAT rule's External Port is the port matched on the public IP, and the Application profile is the translated port on the VM. Both web rules had External Port Any at the same priority, so the HTTP rule ("any port → :80") was catching 443 traffic.
  • FixSet External Port to 80 on the HTTP rule and 443 on the HTTPS rule. The external handshake succeeded immediately.

Phase 3 · Cleaning the database

Step 11Fixed

Padlock up, but images missing

Mixed content: data-bg="http://203.0.113.10/wordpress/wp-content/uploads/…"
  • ReadRead the raw page HTML and found the old IP in banners, slider layers, Open Graph tags and buttons, in http://, https:// and protocol-relative // forms, plus JSON-escaped http:\/\/ inside slider data.
  • PlanBack up the database first, find every column holding the IP, then choose a safe fix per column type.
Step 12Gotchas

Getting a usable backup and query output

  • ErrorUnknown database 'wordpress_db'. Read the real name from DB_NAME in wp-config.
  • ErrorThe dump scrolled to the screen instead of a file: the path was being read as a table name. Fixed with --result-file=.
  • ErrorINTO OUTFILE failed three ways: a stray ; before it, Workbench's "unexpected ordering of clauses", then #1227 Access denied; you need the FILE privilege. Left the FILE privilege alone (a security risk) and wrote results through the client instead.
  • ErrorThe '<' operator is reserved for future use. PowerShell has no input redirection; used -e "source file.sql".
  • CaughtPowerShell treats the backtick as an escape character, so generated SQL had lost its identifier quoting and would fail on columns named key and group. Rebuilt the query file with quoting restored.
  • CaughtA copy-pasted UPDATE had picked up Markdown link syntax, which would have written [www…](https://…) into 371 pages. Added a check for it inside the transaction.
Step 13Fixed

One transaction, verified before commit

  • ScanGenerated a LIKE probe for every text column from information_schema.COLUMNS: 486 columns, 24 of them holding the IP.
  • FixPlain-text and JSON columns updated with nested REPLACE() inside START TRANSACTION, with check queries before COMMIT. Every check returned 0.
  • Kept safeSerialized PHP data (wp_options, wp_postmeta, wp_usermeta) went through a serialization-aware search-replace, since a raw REPLACE changes string lengths and breaks theme settings. Yoast's index tables were rebuilt, not edited. GUIDs and logs were left untouched.

Phase 4 · Routing and redirects

Step 14Fixed

HTTPS redirect that would have dropped the path

  • BugThe original rule redirected to https://{HTTP_HOST}/{R:1}. Inside the /wordpress application, {R:1} is relative to the app, so /wordpress would vanish from every redirected URL.
  • FixRedirect to https://{HTTP_HOST}{REQUEST_URI}, tested as 302 before switching to 301.
Step 15Fixed

Root URL to the WordPress application, without breaking the .NET app

  • ConstraintThe Default Web Site hosts WordPress (PHP), a .NET Framework application and phpMyAdmin. IIS child applications inherit the root's rewrite rules, and the HTTP Redirect feature would redirect all of them.
  • FixOne URL Rewrite rule in the root web.config, conditioned on {REQUEST_URI} matching exactly ^/$. It can never fire inside a child app, so there's no redirect loop. The existing FastCGI handler was kept.

Runbook

Commands and configuration

The commands as run, with hostnames and addresses anonymised. Each one answers a specific question about one hop.

Inspect IIS bindings

Which host names have https bindings, and is SNI on (sslFlags 1)?

Get-WebBinding | Format-Table protocol, bindingInformation, sslFlags
netsh http show sslcert

Who is listening on 443?

PID 4 is http.sys, meaning IIS owns the port.

netstat -ano | findstr :443
tasklist | findstr <PID>

Is port 443 speaking plain HTTP?

If this page loads, whatever answers on 443 is not doing TLS.

http://www.example.com.au:443/wordpress/test.html

Test TLS on the server, bypassing DNS and the gateway

curl.exe, because curl is an Invoke-WebRequest alias in PowerShell.

curl.exe -vk https://www.example.com.au/wordpress/test.html `
  --resolve www.example.com.au:443:127.0.0.1

Find hard-coded addresses in theme and plugin files

Get-ChildItem "C:\inetpub\wwwroot\wordpress\wp-content" -Recurse `
  -Include *.php,*.js,*.css -ErrorAction SilentlyContinue |
  Select-String "203.0.113.10" | Select-Object Path, LineNumber

Check the tables support transactions

SELECT TABLE_NAME, ENGINE FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'wordpress'
  AND TABLE_NAME IN ('wp_posts','wp_revslider_slides','wp_options');

Generate a probe for every text column

Produces one SELECT … LIKE per column. Backticks protect columns named after reserved words.

SELECT CONCAT('SELECT ''', TABLE_NAME, '.', COLUMN_NAME,
  ''' AS location, COUNT(*) AS cnt FROM `', TABLE_NAME,
  '` WHERE `', COLUMN_NAME, '` LIKE ''%203.0.113.10%'' HAVING cnt > 0 UNION ALL')
FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA = 'wordpress'
  AND DATA_TYPE IN ('char','varchar','tinytext','text','mediumtext','longtext');

Rewrite inside a transaction, verify, then commit

Run from the interactive client with source. A session closed before COMMIT rolls back.

START TRANSACTION;

UPDATE wp_posts
SET post_content =
  REPLACE(REPLACE(REPLACE(post_content,
    '203.0.113.10', 'www.example.com.au'),
    'http://www.example.com.au', 'https://www.example.com.au'),
    'http:\\/\\/www.example.com.au', 'https:\\/\\/www.example.com.au')
WHERE post_content LIKE '%203.0.113.10%';

-- same pattern for slider params/layers (JSON) and plugin image columns

SELECT 'posts' AS location, COUNT(*) AS still_has_ip
FROM wp_posts WHERE post_content LIKE '%203.0.113.10%'
UNION ALL
SELECT 'markdown brackets', COUNT(*)
FROM wp_posts WHERE post_content LIKE '%[www.example%';

COMMIT;   -- only when every check returns 0, otherwise ROLLBACK;

Why not REPLACE everything?

PHP-serialized values record each string's length, for example s:12:"203.0.113.10". Swapping in a longer domain without updating that prefix makes the whole value unreadable, and theme settings reset. Those tables went through a serialization-aware tool.

WordPress application web.config: HTTPS redirect

{REQUEST_URI} keeps the /wordpress prefix that {R:1} would drop inside a child application.

<rule name="HTTPS redirect" stopProcessing="true">
  <match url="(.*)" />
  <conditions>
    <add input="{HTTPS}" pattern="off" />
  </conditions>
  <action type="Redirect" url="https://{HTTP_HOST}{REQUEST_URI}" redirectType="Permanent" />
</rule>

Root web.config: send "/" to WordPress only

Matching on {REQUEST_URI} = ^/$ means the inherited rule can never fire inside the .NET or phpMyAdmin applications.

<configuration>
  <system.webServer>
    <handlers>
      <add name="PHP_via_FASTCGI" path="*.php" verb="*" modules="FastCgiModule"
           scriptProcessor="c:\php\php-cgi.exe" resourceType="File" />
    </handlers>
    <rewrite>
      <rules>
        <rule name="Root to WordPress" stopProcessing="true">
          <match url=".*" />
          <conditions>
            <add input="{REQUEST_URI}" pattern="^/$" />
          </conditions>
          <action type="Redirect" url="https://www.example.com.au/wordpress/" redirectType="Permanent" />
        </rule>
      </rules>
    </rewrite>
  </system.webServer>
</configuration>

SSL Settings checked on every application

Require SSL off during migration, client certificates set to Ignore on the site, the WordPress application, the .NET application and phpMyAdmin.

Pin the site address in wp-config.php

define('WP_HOME',    'https://www.example.com.au/wordpress');
define('WP_SITEURL', 'https://www.example.com.au/wordpress');

After the data change

Reset the theme's compiled CSS and JS caches, purged the page cache, rebuilt the SEO plugin's index tables, then re-ran the column scan. Only GUIDs and log tables still held the old address.

Outcome

What changed, and what I'd tell the next engineer

Delivered

  • HTTPS on both apex and www names with a wildcard certificate and SNI bindings
  • Correct DNAT port mapping on the cloud edge gateway
  • HTTP → HTTPS and root → application redirects that are safe for every child app
  • Old IP removed from content, sliders, plugins and settings with zero corrupted rows
  • Verified backup and a repeatable runbook

Risks flagged for follow-up

  • RDP published to the internet: restrict the source to known addresses
  • phpMyAdmin reachable publicly: IP-restrict or remove
  • Search-engine indexing was disabled in WordPress settings
  • Several buttons used root-relative links that skip the application path

Ask the port what it speaks

Sending plain HTTP to :443 turned a vague TLS error into a precise question in one request.

Test from both ends of each hop

--resolve to loopback proved the server healthy. The same test from outside located the fault in between.

Read field labels, not just values

The NAT rules looked right until I read what "External Port" and "Application" actually meant.

Treat data by its format

Plain text, JSON and PHP-serialized columns each need a different replace strategy. Row counts don't tell you which.
